Follow the plan

Build with discipline – do not improvise.

Previously

In Week 7 you planned your signature solution – goal, prompt structure, inputs, evaluation method and risk plan – and pressure-tested a prototype. Today you build it for real.

Words to know

Build, do not improvise

Building means running your approved prompt structure on defined inputs – not inventing a new prompt every time. Record each output before you change anything, so you can see what your solution really does.

The teacher runs the AI on the board. You do not log in, and no prompt ever contains personal or identifying data. Then you evaluate, flag, and change one thing – the loop you record as evaluate → change → result.

Core · Part 2 of 3

Evaluate and flag

Which outputs pass the check?

Evaluate, then flag

Evaluate each output against your check: does it match the known-correct answer from a trusted source, and is it clear? Judge it as correct, unclear or wrong.

A learning system can be confidently wrong, so evaluation is not optional. To flag an output means to mark it for attention instead of quietly accepting it – and a person stays in the loop for anything flagged.

Core · Part 3 of 3

Improve once

One change, one honest result.

Evaluate → change → result

When you find a flagged output, make one improvement – usually a small change to a rule or the prompt structure – then re-run and record the loop as evaluate → change → result.

One change at a time keeps the cause clear: you can see exactly which change fixed the output. Match each flagged problem to the single change that solves it.

Core mission · Worksheet

Build, evaluate, flag, and improve once

Build your solution from your approved plan, run curated inputs on the board, evaluate every output against a trusted source, flag the failures, and log one improvement as evaluate → change → result.

Let's try it

What you need: a Build/Improvement Log with a flag column, a trusted-answer list, curated output cards (two errors) and a pencil.

  1. Restate your goal and check on your log.
  2. Run your prompt structure on defined curated inputs and record each output.
  3. Evaluate each output against the trusted list and flag the wrong or unclear ones.
  4. Make one improvement in response to a flag and re-run it.
  5. Log the loop as evaluate → change → result.
  6. Keep every prompt free of personal data and a person in the loop for each flag.

Tool for this week: teacher-run AI on the board (curated inputs)

The teacher runs the AI on the board – you do not log in. Every prompt uses curated inputs only, and no prompt ever contains personal or identifying data. A person stays in the loop for every flagged output. No live tool? Use curated output cards as the AI responses; pairs evaluate and flag on the cards, rewrite one rule, and predict the new result – fully unplugged.

Week 8 Lab

Extended Build and Evaluation

This is the finish line for your signature solution – but finishing is not just getting one right answer. Today you prove it works across several test inputs, catch any failure gracefully with your fallback, and run a basic risk check. A solution you can measure and defend is one people can trust.

Lab: I can…

  • I can complete a working solution that follows my plan.
  • I can evaluate its outputs across several test inputs and measure accuracy.
  • I can handle an incorrect output gracefully using my fallback.
  • I can run a basic risk check and document the fix I made.

Lab words to know

Tap a card to flip it and reveal the meaning.

Lab · Part 1 of 3

Prove across inputs

One right answer is not proof.

Measure accuracy

One correct answer is not proof. Run your finished solution across a test set – several curated inputs, including a few edge cases – and count how many outputs are correct.

Report accuracy as a simple count, like 5 out of 6, so your claim is honest and checkable. First confirm the build follows the plan and the fallback is wired in, then define what counts as a correct output before you test.

Lab · Part 2 of 3

Handle failures

What happens when an output is wrong?

Catch it gracefully

When an output is wrong, a completed solution does not present a confident wrong answer. Instead the fallback catches it and keeps a person in the loop, and you document the fix and its effect.

As you run the test set, evaluate each output: correct, unclear or wrong. The wrong ones are exactly where your fallback earns its place.

Lab · Part 3 of 3

Run a risk check

Is it accurate, clear, and safe?

The three-question check

Finish with a basic risk check that asks three questions: is the solution accurate enough for its purpose, are the outputs clear enough to act on, and does any prompt contain personal or identifying data?

In a teacher-mediated classroom the AI runs on the board with curated inputs, so the data answer must always be no. Then document the biggest remaining risk and who should check it.

Lab mission · Worksheet

Complete, test across six, and risk-check

Complete your solution, run it across six curated test inputs, measure accuracy, handle any failure with your fallback, document the fix, and finish with a three-question risk check.

Let's try it

What you need: a Test-Set Evaluation Log (six rows), six curated test-input cards, a Basic Risk-Check Card and a pencil.

  1. Confirm your build follows the plan and the fallback is wired in.
  2. Define what counts as a correct output for your goal.
  3. Run all six curated inputs on the board and record each result.
  4. Compute accuracy (correct out of six) and handle any failure with your fallback.
  5. Document the fix and its effect.
  6. Complete the three-question risk check and note the biggest remaining risk.

Tool for this week: teacher-run AI on the board (six curated test inputs)

The teacher runs the AI on the board with the six curated test-input cards – you do not log in, and no prompt contains personal or identifying data. When an output is wrong, the fallback hands it to a person. No live tool? Use six curated output cards as the AI responses; pairs evaluate accuracy, act out the fallback for a failing card, and complete the same risk check with no live tool.

Lesson summary

You built the real solution from your plan, improved it with evidence, and measured how far it can be trusted

Key ideas to remember

  • Building means following your approved plan and running defined inputs, not improvising.
  • Evaluate every output against a trusted source and flag anything wrong or unclear.
  • A learning system can be confidently wrong, so checking is never optional.
  • Make one improvement at a time and record it as evaluate → change → result.
  • One correct answer is not proof – run a test set and report accuracy as an honest count, like 5 out of 6.
  • A completed solution handles a wrong output with its fallback and keeps a person in the loop.
  • A basic risk check asks: accurate enough, clear enough, and no personal data used?

Glossary

Build
running your approved prompt structure on defined inputs to make the solution.
Evaluate
checking each output against a trusted source for accuracy and clarity.
Flag
marking an output for attention because it is wrong or unclear.
Evaluate → change → result
the loop of judging an output, making one change, and recording what happened.
Test set
a small collection of curated inputs used to measure a solution's accuracy.
Accuracy count
how many outputs are correct out of the total, like 5 out of 6.
Graceful handling
catching a wrong output with the fallback instead of stating it confidently.
Risk check
three questions about accuracy, clarity, and personal data.
