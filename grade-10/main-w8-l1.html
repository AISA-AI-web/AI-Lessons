Building means assembling your components

Building is not the moment to redesign. It is the moment to assemble the components you already planned – your data, your tools and your prompts – so they interact in order. Set up each component, then connect the hand-offs so one part's output becomes the next part's input. Keep your design open beside you and trace the flow as you go, thinking of the whole thing as one system. If a hand-off is unclear, fix that one connection first, then keep going. No names, faces, voices or personal details go into any data or prompt.

Core · Part 2 of 3

Hold out, then evaluate

How do you test a system fairly – and judge what it says?

Keep a held-out test set

Before you tune anything, set aside a few inputs as a held-out test set – and do not use them to build or improve the system. You will only run them at the very end. Why? If you tune your system on the same inputs you test it on, you learn those inputs, not the task. A held-out set that the system has never seen is the only fair way to check it will work on new cases, not just the ones you practised on.

Evaluate against criteria and governance

When your integrated output appears, do not trust it just because it reads smoothly – a fluent system can still break a rule. Check it against every success criterion and governance expectation – accurate, appropriate, and keeping personal data out. Verify one claim against a trusted source. Then find one criterion it misses and change a single component – a prompt, an input, or a hand-off – and run it again.

Core · Part 3 of 3 · Worksheet

Improve one part

How do you prove a change helped?

Changing only one part lets you prove which change made the output better, which is how good systems are refined. If you change the prompt, the data and the tool together and the output improves, you cannot say which change did it – or whether one of them made something else worse.

Why it matters

The integrated AI systems the UAE relies on only work when someone assembles their parts carefully, checks outputs against clear rules, and improves them with evidence – and tests them on cases they were not tuned on. (Illustrative context.) That is the discipline you practise today.

Cross-curricular link · Mathematics · Design & Technology

Scoring each output against a fixed criterion and marking pass or fail is measurement against a standard in Mathematics. Building from a plan and improving one change at a time is the make-and-test cycle from Design & Technology.

Lab · Part 1 of 3

Finish, then test more than once

When is a system dependable – not just lucky?

Finish the system, then test it more than once

A system that worked one time is not finished – its components may have aligned by luck. You complete every component so the system runs from data to output, then test it again with different inputs, including your held-out set and a deliberate edge case – a very long, an incorrect, or a blank input. Each time, check the output against your criteria and governance rules. Keep personal details out of every input, and let the teacher run the AI step. An edge case that breaks your system is useful – it shows exactly which component to strengthen.

Lab · Part 2 of 3 · Worksheet

Keep an evaluation log

Which improvement really helped – and how do you know?

Keep an evaluation log and handle edge cases gracefully

Every test goes in your evaluation log: the input, the output, which criteria and governance rules it met, the single component you changed, and what that change did. A log lets you compare runs and see which improvement really helped. When an unusual input makes your system go wrong, do not ignore it – adjust the responsible component so the system responds sensibly, then record the fix. A fluent output still gets checked against a trusted source. Aim for several logged cycles, not one – that is what it means to iterate.

Why it matters

Reliable integrated services people across the UAE depend on are tested again and again, and made to fail safely on odd inputs, before release. (Illustrative context.) An evaluation log is how builders prove a system's components really work together and stay within the rules.

Cross-curricular link · Mathematics · Design & Technology

An evaluation log of repeated runs is a data table you read for trends in Mathematics. Designing so the system fails gracefully on an awkward input is robust design from Design & Technology.

Tool for this week: approved assistant (build), with an optional Colab / no-code extension – teacher-mediated

1. Finish assembling every component so the system runs from data to output. 2. Test with a normal input, an edge case, and a held-out input; score each against criteria and governance rules. 3. Refine one component, re-run, and add a new row to your evaluation log each time. Stay safe: approved, teacher-managed assistant only; no personal data. Verify outputs against trusted sources and disclose AI use.

Lesson summary

Build it, judge it, improve it – then prove it holds up

  • Assemble the components you planned; fix unclear hand-offs as you go.
  • Keep a held-out test set you never build or tune on, for a fair final check.
  • Evaluate against every criterion and governance rule; verify a claim against a trusted source.
  • Refine one component at a time so you can prove which change helped.
  • A system that worked once is not finished – test it again on varied inputs.
  • Test an edge case and a held-out input; make the system fail safely.
  • Keep an evaluation log so improvements become comparable evidence.
  • Iterate: test, evaluate, refine, log – several cycles, not one.
