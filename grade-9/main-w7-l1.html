Designing the System + Prototype and Pressure-Test

Today you become the architect of your signature solution – not just a line of steps, but a system whose parts work together. You plan how the data, the tool and the prompt interact, and set the bar the final output must clear. Then, in the Lab, your system meets reality: you walk it through as a prototype, weaken one part on purpose to see how far the damage spreads, and add a fallback for when a check fails.

Focus: Plan your signature solution – all four strands  ·  Role: Solution Architects

  • Map the system. I can write a clear goal and map my solution as interacting components – data, tools and prompts – in ordered steps with success criteria and check steps.
  • Trace the interactions. I can name the inputs, the teacher-operated tool and the non-personal data each component uses, and show how one step's output becomes the next step's input.

  • Lab: prototype and pressure-test. I can walk my whole system through once, weaken one component on purpose and trace how the problem spreads, and add a fallback path for when a check fails – with no personal data and no student logins.

Core · Part 1 of 3

System, not a list

What turns steps into a system?

Previously

Last week (Week 6) you ran a workflow end to end, scored its reliability, and saw which part let it down. Now you design your own signature solution as a system whose parts work together.

Words to know

Tap a card to flip it and reveal the meaning.

A solution is a system

Your signature solution is a small system with three kinds of component: the non-personal data it uses, the teacher-operated tool that does the work, and the prompt that tells the tool what to do. Planning means designing how these components interact before you build.

You write a clear goal, then map the components as ordered steps with arrows, so the output of one component becomes the input of the next. Change the prompt and the tool's output changes too. Seeing those connections is what makes it a system, not just a list.

Core · Part 2 of 3

Components interact

Whose output feeds whom?

Each part has a job

A system has parts that each do one job. The non-personal data is what the system works from, the teacher-operated tool does the processing, and the prompt directs that tool. A check step then judges the final output.

Because the components are connected, the output of one becomes the input of the next. Naming each part and its handover is how you show the system really interacts, rather than sitting as separate boxes. It also shows you something important: a weak part does not stay on its own – its problem flows on to every component downstream.

Why it matters

Across the UAE, teams building integrated systems – from smart-city dashboards in Dubai to logistics tools at the ports – plan how each part connects and set clear numbers before anyone relies on the whole system. Designing the interactions, and keeping them responsible, is what makes an AI solution trustworthy.

Core · Part 3 of 3 · Worksheet

Set the bar, plan for risk

Can you trust an output on sight?

Criteria, check and mitigation

Because your components are connected, a weak part spreads its problem downstream: poor data or a vague prompt gives the tool a poor output, and every step after it suffers. So your plan sets success criteria – a measurable bar, such as 9 correct out of 10 – and a check step that judges the final output against that bar instead of trusting it on sight.

Then you name one risk to the system and the mitigation that reduces it. As a stretch, add a fallback: what your system does when a check fails, so a wrong output never flows on. Throughout, the design stays account-free and uses no personal data.

Tool for this week: unplugged simulated-AI cards (teacher-led)

This is an unplugged concept lesson: the teacher runs a simulated-AI card routine on the board – no live tool, no logins. Students reason about pre-prepared example outputs on the cards; no personal data is used. Use the worksheet to sort or judge the cards and explain your thinking with the key vocabulary. The live tools (Teachable Machine and Scratch) are used in the matching Lab period. No demo tool? Run the tool component as a simulated AI: a sealed envelope of pre-written response cards a partner draws from in reply to your written prompt, so the whole system can still be mapped and traced with no device.

Solution Architects: map the system (away from the screen, in pairs)

  1. Write your goal in one sentence: what defined problem will your system solve?
  2. List the components: the non-personal data, the teacher-operated tool, and the prompt that drives it.
  3. Draw the ordered steps and connect them with arrows so each component's output feeds the next.
  4. Set your success criteria: how good must the final output be, as a number or comparison?
  5. Add a check step that judges the output, then name one risk with a mitigation the plan uses.
  6. Draw a dashed arrow showing which downstream components are affected if that risk hits.
Week 7 Lab

Prototype and Pressure-Test

In the Core period you planned your signature solution as coupled parts with success criteria and checks. Today your system meets reality: you run it as a prototype, weaken one part on purpose to see how far the damage spreads, and make it safer with a fallback for when a check fails.

Words to know

Lab · Part 1 of 3

A map is a guess

Do the parts really connect?

Walk it through by hand

Your Core map looks neat on paper, but paper hides broken connections. A prototype is the first time you actually run it: you take one real, non-personal input and walk it through every component in order – data, prompt, tool – saying at each arrow what output is handed to the next.

At the check step, you judge the output against your success criteria. Where one component's output cannot really be used by the next, you have found a broken interaction – and finding it now, by hand, is exactly the point. Prototyping turns a guess into something you have seen connect.

Lab · Part 2 of 3

Weaken one part

How far does a fault travel?

Pressure-test the system

Because your components are coupled, a fault in one spreads downstream – it propagates. To really trust your system, you weaken one component on purpose – give the tool a vague prompt, or feed it a poor data example – then trace how far the problem travels and measure the output at your check step.

Did the check catch a result below the criteria? If a poor output slipped through, you tighten the check. Pressure-testing is how engineers decide what to improve before anyone relies on the whole system.

Why it matters

Engineers testing integrated systems in the UAE – smart-city networks, port logistics, health tools – deliberately weaken one part to see how failures spread, and measure against strict numbers, before anyone relies on the whole system. Pressure-testing and fallbacks are how a smart solution earns trust.

Lab · Part 3 of 3 · Worksheet

Build a fallback

What happens when a check fails?

Fail safely, stay account-free

A strong system degrades gracefully. You build a fallback path – you decide which check triggers it and exactly what the system does the moment that check fails: reroute to a safer component, flag the output for a human, or return to the input.

That way a wrong output never flows on. Throughout, every tool step stays teacher-operated and account-free, and only non-personal example inputs enter the system.

Lesson summary

Design the system – then see it connect, break and recover

  • A signature solution is an integrated system of components – data, tool and prompt – not just a list of steps.
  • The components are coupled: the output of one becomes the input of the next, so a weak part degrades everything downstream.
  • Success criteria set a measurable bar, and a check step judges the final output against it before it is trusted.
  • A named risk with a mitigation keeps the design robust, responsible and account-free.
  • A system map is only a hypothesis; a prototype walk-through shows whether the components really connect.
  • Pressure-testing weakens one component on purpose to trace how a failure propagates; if a poor output slips past the check, tighten the check.
  • A fallback path – a named trigger and a safer action – makes a coupled system fail gracefully. Next week (Week 8) you stop planning and assemble your parts into one working system.
