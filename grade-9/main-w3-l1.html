Designing a Solution + Build, Test, Chain

Today you become a designer. You take a defined problem and design a structured workflow whose components – data, prompt and tool – work together to solve it, then test whether the solution really holds. Then, in the Lab, you get real build time: you fix the weakest component one change at a time, chain a second tool step, and prove the solution is reliable across two datasets.

Strand: Solution Design  ·  Role: Solution Architects

Two lessons in oneStart with the Core: Designing a Solution, then move on to the Lab: Build, Test, Chain.

What you will learn

  • Design it. I can design a structured workflow in which data, a prompt and a tool work together to complete a defined task.
  • Build and justify. I can build and run the workflow and justify why each component gave the result it did.
  • Use the words. I can use terms like component, data, prompt, tool and interaction correctly to explain how my solution fits together.
  • Lab: build, test, chain. I can construct a multi-component workflow and test it until it solves my defined problem, find the component that lets it down and change one thing at a time, and use design vocabulary to justify why my solution is reliable.

Components that interact

Why is a solution not one magic step?

Previously

In Week 2 you tested a system and justified which component mattered most to the output. Now you design a solution of your own.

Words to know

A solution is components that interact

A structured AI solution is not one magic step – it is a set of components that interact. You supply data, you write a prompt that tells the tool what to do, the tool does the work, and you evaluate the output against the problem you defined. The interactions are the point: a vague prompt gives the tool nothing useful to do, and messy data gives a messy output no matter how good the tool is. When you design, you specify each component and think about how a change in one ripples through the others.

Core · Part 2 of 3

Define, then build

What has to come first?

A good designer defines the problem first

Before building anything, a designer states the defined problem clearly – what counts as a good solution. That definition tells you what data you need, what the prompt must ask for, and what a correct output looks like. Then you build and test: run the workflow and verify that the output actually solves the defined problem, checked against a trusted source. If it fails, you know which component to adjust because you know what each one was meant to do.

Why it matters

Across the UAE, organisations build structured AI workflows to triage messages, screen documents and plan services – always as interacting components that are tested before anyone trusts them. Learning to design and evaluate one now means you can shape these solutions, not just use them.

Designing the workflow follows the design process: write a clear brief (the defined problem), specify each component like materials and tools, build a prototype, then evaluate the output against the brief and refine the part that let it down.

Core · Part 3 of 3 · Worksheet

Verify, don't trust

Can you trust a confident output?

Check the components, not the polish

Even a confident output can be wrong, so you check the components rather than trusting how polished the result sounds. Verifying against a trusted source is what turns a good-looking answer into a solution you can stand behind. Using the words component, data, prompt, tool and interaction correctly lets you say exactly where a problem could enter – and which component to adjust when it does.

Solution Architects: design the four-component workflow (away from the screen)

You need a problem menu card, component cards (data, prompt, tool, output), a simulated-AI card deck, a trusted-source reference sheet and a pencil. Choose one defined problem and write, in one line, what a good solution looks like. Specify your data – exactly what you will supply, with no personal data. Write your prompt so the tool knows exactly what to do with the data. Place the tool card that matches your prompt and run the workflow. Record the output and note one interaction between two components. Evaluate the output against the problem and a trusted source, then tick or fix each component. No cards? One student is the tool and follows the pair's written prompt exactly, using only the supplied data, while the others evaluate the output.

Week 3 Lab

Build, Test, Chain

In the Core you designed a workflow whose data, prompt and tool work together. Now you get real build time: test it, fix its weakest component, then grow it into a multi-component solution that does more than one job – and prove it solves your defined problem reliably.

Words to know

Tap a card to flip it and reveal the meaning.

Lab · Part 1 of 3

Change one thing

How do you know which change helped?

Improve by changing one component at a time

The fastest way to improve a solution is not to rebuild it. You test it on fresh data, find the one component that weakens the output – often the prompt or the data – and change only that. Because the components interact, that single change ripples to the others, so keeping it to one change is how you know which interaction helped. Then you run it again and compare against the defined problem. Notes of before and after turn guessing into evidence. This is iteration: a controlled loop that makes your build better and lets you justify exactly why.

Why it matters

Real UAE solutions – screening documents, routing customer requests, planning logistics – are built as chains of interacting components and are tested across many datasets before anyone trusts or governs them. Building and testing a chain now is exactly this professional skill in miniature.

Lab · Part 2 of 3

Chain the steps

Does the hand-off hold?

Chain components to do more

A multi-component solution does more than one job by chaining tool steps. The structured output of the first tool becomes the input of the second – that join is the hand-off, and it depends on the first step returning something the second can use. So when you test a chain you check three things: does each component do its part, does the hand-off hold, and does the whole solution address the defined problem. A weak hand-off is fragile; a mismatched one is broken.

Cross-curricular link · Physical Education

A relay race models the multi-component chain: each runner's baton hand-off must pass cleanly to the next, and a coach improves the team by drilling one leg at a time, then re-testing the whole chain – just like iterating a workflow.

Lab · Part 3 of 3 · Worksheet

Prove reliability

One good run – is that enough?

Reliable means it holds across datasets

A solution is reliable only when it holds across more than one dataset, so always test with at least two, and verify each output before you trust the chain. One success can be a fluke. Using words like iterate, hand-off, reliable and verify precisely lets you justify not just that your solution works, but why – and that is what makes it easier to trust and to govern.

Solution Architects: iterate, then chain (away from the screen)

You need your Core workflow cards, a second set of tool cards, two non-personal datasets, an iteration log (before / after) and a trusted-source reference sheet. Run your Core workflow on a fresh dataset and judge the output against the defined problem. Mark the one component that weakens the solution – often the prompt or the data. Change only that component, run again, and log the output before and after. Add a second tool card so your structured output becomes the next input. Run the whole chain on two different datasets, verify each output against the problem and a trusted source, and record which change helped most. No devices? One student is Tool A and another is Tool B; pass A's written output to B by hand to show the hand-off, while the rest verify.

Lesson summary

Design a solution of interacting components – then iterate, chain and prove it holds

  • A structured solution is components – data, prompt, tool, output – that interact; a change in one ripples through the others.
  • Define the problem first, then build, run and evaluate.
  • Verify against a trusted source – a confident output can still be wrong.
  • Change one component at a time so you know which interaction helped; notes of before and after turn guessing into evidence.
  • A chain works only if each hand-off returns what the next stage can use.
  • Reliability is shown across more than one dataset, then verified.
