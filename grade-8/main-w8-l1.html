Building is testing

Run, evaluate, improve, repeat

Building your solution does not mean finishing it in one go. You assemble the steps from your plan, run them on test inputs, and read what comes out. Then you compare that output to your criteria – one by one – and mark each as pass or not-yet.

This is a loop, not a single act: run, evaluate, improve, then run again. A solution that runs is only halfway there; a solution you have tested against clear criteria is one you can actually trust. Any AI step is run by your teacher at the board, and you never enter personal data such as names, faces or voices.

Core · Part 2 of 3

Evaluate honestly

Does a confident output pass?

Judge, do not trust

AI outputs often sound sure of themselves. Fluent and detailed is not the same as correct. That is why you verify before you trust: check each output against your criteria and against a source you already trust.

Evaluating means scoring each output honestly – pass or not-yet – with one word of evidence. An output can pass one criterion while failing another, so you judge them one by one.

Why it matters

Across the UAE, teams building smart tools – from Arabic-language helpers to traffic and energy systems – only ship them after testing outputs against strict criteria. Learning to evaluate and improve, not just build, is exactly how that real work is done.

Cross-curricular link · Islamic Studies

Connect verify-before-trust to the Islamic principle of tabayyun – checking a report's truth before acting on it (Surah Al-Hujurat 49:6) – so you never accept a confident-sounding output without checking it against a trusted source.

Core · Part 3 of 3 · Worksheet

Improve with evidence

What makes a change worth keeping?

When something fails, that failure is useful – it points to exactly what to improve. A good improvement is one you can trace back to evidence: this criterion failed, so I changed this, and on the re-run it passed.

Random changes just move the problem around. Pick the criterion that failed most, change one thing to target it, then re-run and record the before-and-after so you know whether the change actually helped.

Tool for this week: unplugged simulated-AI cards (teacher-led)

This is an unplugged concept lesson: the teacher runs a simulated-AI card routine on the board – no live tool, no logins. Students reason about pre-prepared example outputs on the cards – no personal data is used – and use the worksheet to sort or judge the cards and explain their thinking with the key vocabulary. The live tools (Teachable Machine and Scratch) are used in the matching Lab period. No device? The AI step becomes a paper rule card or a pre-printed output deck: draw the matching card for each input, score it against the criteria, and swap one rule card as your improvement.

Lab · Part 1 of 3

The log leads

What turns testing into improvement?

Anyone can change their solution; the log is what makes a change worth trusting. For each test input you write the output, a pass or not-yet against every criterion, and one word of evidence.

When you look down the log and see the same criterion failing again and again, you know exactly where to work next. That is how real teams prioritise – by evidence, not by which problem is loudest. Keep any AI step teacher-run, use no personal data, and verify each output against the criteria and a trusted source before you believe it.

Lab · Part 2 of 3

Choose the move

Which lever does each change pull?

When the log shows a criterion failing, you pick an improvement move and apply just one at a time. Each move pulls a different lever: you can change the data, change a step, add a check, or change the tool.

Knowing which move targets which problem is what keeps your changes deliberate. Apply one, re-run, re-score, and log the before-and-after so you can see whether the move helped.

Why it matters

Whether it is a delivery app, a health screening tool, or a smart-city sensor in the UAE, the difference between a demo and a product is a tested solution with a log and safe handling of odd inputs. That is the standard you are practising here.

Lab · Part 3 of 3 · Worksheet

Fail gracefully

How should a solution meet a bad input?

A strong solution is not one that never meets a hard input – it is one that handles a hard input well. Feed yours something tricky on purpose: a blank field, an unknown value, something outside what you planned for. This is an edge case.

A weak solution gives a confident wrong answer; a strong one says clearly that it cannot match the input and asks you to check. When you find a case like that, fix it and write the fix in your log so the solution fails gracefully next time. Documenting the fix is part of the engineering, not an extra.

Cross-curricular link · Computing

Like handling invalid input in a program, test edge cases such as a blank or unexpected value, make the solution fail gracefully with a clear message instead of a confident wrong answer, and keep a test log.

Lesson summary

Build, log honestly – then improve with evidence

  • Building is a loop: run, evaluate, improve, then run again.
  • Evaluate each output against the criteria and a trusted source, one by one.
  • A confident, fluent output can still fail a criterion – verify before you trust.
  • A good improvement traces back to a specific gap the evaluation exposed – change one thing at a time.
  • A solution is finished when it runs end to end and has been evaluated across inputs; the evaluation log records output, per-criterion score and evidence for each input.
  • Patterns in the log show which criterion to iterate on next, and a strong solution fails gracefully on an edge case, with the fix documented.
