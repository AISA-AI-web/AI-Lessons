Build, Evaluate, Improve + Finish It, Then Prove It

Today you stop planning and start building. You run your solution for real, look hard at what it produces, and make it a little better. Then, in the Lab, you finish it so it runs all the way from input to output – and you test it enough times to know you can trust it.

Focus: Build – Solution Design and Critical Evaluation, with safe testing (Ethics & Governance)  ·  Role: Systems Detectives  ·  Tools: Core – unplugged simulated-AI cards; Lab – Teachable Machine + Scratch (teacher-operated)

What you will learn

  • Build by the plan. I can build my solution by following my input, process and output plan.
  • Evaluate. I can test my solution and judge its outputs against our success criteria.
  • Improve one thing. I can make one clear improvement after looking at what my evaluation shows.
  • Lab: finish and prove it. I can finish a working version that runs from input to output, test it more than once, and log how each output scores against the criteria.
  • Lab: keep a log. I can make and record several improvements and say what each one changed.

Building means following your plan

Building is not the time to invent a brand-new idea. It is the time to follow the plan you already made, like following a recipe. You prepare your input, run the process step, and get your output.

Keep your plan open beside you and point to each part as you do it. If a part of the plan is unclear, fix that small part first, then keep going. Remember: no names, faces or personal details ever go into your input.

Why it matters

AI tools in the UAE, from smart government apps to school helpers, are only useful when someone builds them carefully and checks their outputs – the same habit you are practising today.

Core · Part 2 of 3

Evaluate the output

Can you trust a confident output?

Judge against the criteria

When your output appears, do not just trust it because it looks confident – a sure-sounding answer can still be wrong. Check it against each success criterion and against a trusted source.

Some outputs clearly meet a criterion. Some clearly fail it. Others could be right but must be verified against a trusted source before you accept them.

Core · Part 3 of 3 · Worksheet

Improve one thing

Why change only one thing at a time?

One change, then re-run

Find one criterion your output does not meet. Then change one thing – either the words of your input or a single step – and run it again.

Changing only one thing lets you see whether that change is what made the output better. Note what you changed, why, and whether the new output met the criterion it was aimed at.

Cross-curricular link · Science

Building and improving your solution uses the science fair-test rule: change only one variable – one word of the input or one step – then re-run, so you can tell which single change actually improved the output.

Tool for this week (Core): unplugged simulated-AI cards (teacher-led)

This is an unplugged concept lesson: the teacher runs a simulated-AI card routine on the board – no live tool, no logins. You reason about pre-prepared example outputs on the cards, and no personal data is used. Use the worksheet to sort or judge the cards and explain your thinking with the key vocabulary. The live tools (Teachable Machine and Scratch) are used in the matching Lab period. No tool? The input is a question card, the process is a lookup table applied by hand, and the output is the matching answer card – evaluate and refine the same way.

Hands-on mission: run the build loop

  1. Open your plan and success criteria side by side and read them aloud.
  2. Prepare your input exactly as planned, with no names or personal details in it.
  3. Run the process step and write down the exact output you get.
  4. Tick or cross the output against each criterion and verify one claim against a trusted source.
  5. Change one thing, run it again, and note whether the new output met the criterion.
  6. Log it: write what you changed, why, and whether it worked.

Finish It, Then Prove It

Tool for this week (Lab): Teachable Machine + Scratch – train a model, then wire it into a Scratch workflow

  1. First train the model in Teachable Machine: name the classes, add balanced examples, click Train, then test in Preview.
  2. Open Scratch (account-free) and add the machine-learning blocks so the trained model becomes the process step.
  3. Wire the workflow: input (what you feed in) → model (classifies) → output (what Scratch shows).
  4. Click the green flag to run the whole system end to end.
  5. Test with new inputs; if the output is wrong, improve the model's examples or the Scratch logic, then run again.
  6. Save the Scratch project as an .sb3 file.

Stay safe: 🔒 the teacher operates the tools on the board; students never log in; non-personal data only. Teachable Machine trains in the browser and the samples stay on the teacher's device. Use objects, hand gestures or drawings only – never faces, voices or names. Clear the project at the end of the lesson. Only the non-personal model is used.

No tool? Run the simulated-AI card set: a lookup table is the process, and you swap several input cards – including a tricky one – logging and refining exactly as you would with a tool.

Cross-curricular link · English

Iterating your solution mirrors the writing process: draft, test on tricky sentences, and redraft. Keep an evaluation log like a writer's revision record, checking each version against success criteria as you would edit a piece against a checklist.

Lab · Part 1 of 3

Finish, then test

Is one good run enough?

One run is not proof

A solution that worked one time is not finished – it might have been lucky. In the Lab you complete every step so it runs from input to output, then you test it again with different inputs.

Try an awkward one on purpose, like a very long or a blank input. Each time, check the output against your success criteria, keep personal details out of every input, and let the teacher run the AI step.

Why it matters

Reliable apps that people across the UAE depend on are tested again and again before release; keeping an evaluation log is how builders prove a solution really works.

Lab · Part 2 of 3

Keep a log

How do you compare runs fairly?

Keep an evaluation log

Every test goes in your log: the input you used, the output you got, which criteria it met, the change you made, and what that change did. A log lets you compare runs side by side and see which improvement really helped.

It also helps you stay honest – a confident output still gets checked against a trusted source before you trust it. Aim for several logged cycles, not one.

Lab · Part 3 of 3 · Worksheet

Test the inputs

Which inputs are safe to try?

Sort before you test

Some inputs are normal tests; some are awkward edge cases you try on purpose; and some must never be used at all.

Use objects, gestures or drawings – never faces, voices or names. A confident output still gets checked against a trusted source before you trust it.

Hands-on mission: iterate and log

  1. Find where your build stopped and finish every step so it runs from input to output.
  2. Prepare a first test input with no names, faces or personal details, run it, and record the output.
  3. Test again with a different input, including one awkward or edge-case input.
  4. Score each output against your criteria and verify one claim against a trusted source.
  5. Refine one part, re-run, and add a new row: input, output, criteria met, change, effect.
  6. Repeat the cycle until your solution meets the criteria across more than one input.

Reflect · Responsible use & human in the loop

The AI tool does the sorting or drafting, but a person stays in charge. Think about where a person decided or checked in today's workflow, whether it could treat someone unfairly or be misused, and how what you built is different from what an AI would produce on its own.

Lesson summary

You built it, evaluated it, improved it – then finished it and proved it

Key ideas to remember

  • Building means faithfully following your plan, like a recipe – not inventing a new idea.
  • An output is evaluated against every success criterion and a trusted source, not trusted on sight.
  • A confident-looking output can still fail a criterion, so it is not finished.
  • You improve by changing one thing, aimed at the missed criterion, then running it again.
  • A solution is complete when it runs from input to output with no gaps.
  • One good run may be luck; reliability is proven by testing on several inputs.
  • Edge cases – long, blank or awkward inputs – reveal weaknesses that normal inputs hide.
  • An evaluation log traces each input, output, criteria met and change, across several cycles.

Glossary

Build
follow your plan step by step to make the solution actually run.
Evaluate
judge an output by checking it against your success criteria.
Success criteria
the short list that says when an output is good enough.
Verify
check an output against the task and a trusted source before you trust it.
Refine
change one part of your input or structure to improve the output.
Complete
the solution runs all the way from input to output with no gaps.
Reliable
it keeps meeting the criteria on different inputs, not just one.
Edge case
an unusual or awkward input that can break a solution.
Iterate
repeat the test, evaluate, refine and log cycle to make it better.
