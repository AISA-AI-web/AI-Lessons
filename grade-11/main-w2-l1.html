Understanding the System

Every AI solution you meet turns an input into an outcome, but never on its own. Today you open a solution up and see the broader system around it – data sources, tools and users interacting – so you can explain, and later optimise, how any solution really works. Then, in the Lab, you become the tester: trace one input, change one part at a time, and work out which interaction moves the outcome and its performance.

An AI solution lives inside a broader system

Look at a real AI solution and the model is only one part. Around it sits a broader system: a data source the tool learned from, other tools that pass information along, and a user who acts on the result. An input flows through all of them and an outcome comes out the other end. The parts interact, which means each one affects the next – the data source shapes what the tool can do, and the user decides what happens to its output. Once you can see the whole system, you can explain how a solution works rather than treating it as magic.

Core · Part 2 of 4

How the model works – and how the parts interact

Training, pattern, inference – then follow the interaction to the outcome.

How the model part actually works

The model at the centre is not magic. It was built from training data – many past examples – from which it learned a pattern. When a new input arrives, the model applies that pattern to produce an output: this step is called inference. Knowing this helps you see why the data source matters so much: if the training data was narrow, the learned pattern – and every inference from it – will be narrow too.

Follow the interaction to the outcome

Describing a solution is more than naming its model – it is following how the parts interact to make the outcome. Ask what the input was, what the data source let the tool learn, how another tool passed it on, and how the user responded, then reason about why that produced this outcome rather than another. This is analysing, not just listing. When you can trace the interaction, you can say which part shaped the outcome most and where performance could be improved – the first move a designer makes before optimising a solution. It is also why you verify an outcome instead of trusting it.

Why it matters

AI solutions across the UAE – smart-clinic triage assistants, port-logistics routers, Arabic–English service chatbots – are all embedded in broader systems of data, tools and people. Seeing how those parts interact lets you understand, question and optimise the solutions you meet, and the one you will build for performance this term.

Cross-curricular link · Mathematics · Biology · Computer Science

Turning raw input into the numbers a model reads is data representation in Mathematics. The neural network adjusting connection strengths is loosely modelled on neurons in Biology. Separating one-off training from everyday inference is a key idea in Computer Science.

Lab · Part 1 of 3

Trace one input through every part

One input, every part, written down.

Tracing means picking one input and following it through the whole system. You watch the data source set what the tool can do, see the tool apply it, notice how another tool passes it on, and see how the user responds before an outcome is acted on. Writing down each part for the same input keeps you honest – it stops you mixing up two different items. A clear trace is how a tester proves they know what a solution really does, not just what they hope it does. It is also the record you compare against when you start changing parts.

Change one part, or you cannot trust the comparison

If you change two parts at once and the outcome improves, you cannot say which change caused it. Keep everything the same except one part, run it again, and compare – this is a controlled change, and it turns ‘I think it got better’ into evidence you can defend.

Why it matters

Testers who change parts on purpose find problems before real users do. This is how teams in the UAE check an AI service performs fairly and reliably – across different data sources, tool settings and user responses – before it is switched on for the public, and it is the discipline behind your own Term 1 optimised solution.

Cross-curricular link · Science · Mathematics

Changing one part while holding the rest constant is a controlled experiment in Science. Recording comparable before-and-after outcomes is data handling in Mathematics.

Lab · Part 2 of 3 · Worksheet

Change one part, compare the performance

Same request, one part changed per run. What changed, which part caused it, and what happened to performance?

Here is the tester's method: keep everything the same except one part, run it again, and compare. Change only the user's response, or swap the data source the tool learned from, and watch the outcome. If the outcome moves, that part and its interaction affect performance – its accuracy, speed or usability. Change one thing at a time so you know what caused the change. Some parts move performance a lot, others barely at all – and justifying which one matters most is the analysis a designer needs before optimising a solution. Before you trust any outcome, verify it against something you know is correct.

Lesson summary

See the whole system – then trace, change one part and compare

  • An AI solution sits inside a broader system: a data source, the model, other tools, an interface and people.
  • The model learned a pattern from training data and applies it to new inputs – that step is inference.
  • Describing a solution means following the interaction from input to outcome, not just naming the model.
  • A narrow data source produces a narrow pattern, so the data shapes performance downstream.
  • Tracing follows one input through every part so you can see each part's effect.
  • A controlled change – one part at a time – lets you attribute a difference to its cause; the part that most changes the outcome is the one that most affects performance.
  • Always verify an outcome against a trusted answer before trusting it.
