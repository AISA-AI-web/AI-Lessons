Build, Evaluate, Improve

Today you turn your plan into a working solution. Building is not finished when it runs – it is finished when it runs and meets your criteria for efficiency, usability and performance. Then, in the Lab, your prototype becomes a finished, dependable solution: you complete every stage, run it again and again, keep an evaluation log, and make it behave well even when the input is awkward.

Strand: Signature Solution · Build  ·  Scenario: building and completing your signature solution

📅 When to teachWeek 8 of Term 1 – Monday 23 to Friday 27 November 2026. Grade 11 has one AI period a week: Boys 11 on Wednesday 25 November, Girls 11 on Friday 27 November. Core lesson first, then the Lab.
Two lessons in oneStart with the Core: Building, then move on to the Lab: Finish It, Then Prove It.

What you will learn

  • Build from the plan. I can build my solution step by step by following my plan and structure.
  • Evaluate against criteria. I can test my solution and judge its outputs against my success criteria.
  • Improve one thing. I can improve my solution by changing the structure or an input, and say why the change helps.
  • Lab: complete, log, handle an edge case. I can complete a working version of my solution, keep an evaluation log that scores each run against my three criteria, and handle an awkward input gracefully, writing down each fix.

From plan to working build

You already have a plan: a goal, a structure of steps, the inputs, the check steps and your success criteria. Building means assembling that structure for real, one step at a time, and keeping your check steps in place as guards. Feed it a real input – but never any personal data, no names or faces. When the solution runs and produces an output, you have a build to test. Running is the start of the work, not the end of it.

Core · Part 2 of 3

Evaluate against a check the build has not seen

Fluent is not the same as correct.

Score your output honestly against each success criterion – efficiency, usability, correctness – using an input the build was not tuned on. A fluent, confident answer can still be wrong, so verify before you trust: check it against a trusted source. Then improve one thing at a time – the structure or a component – and log what changed, so you know the improvement was real and not luck.

Verify before you trust

A confident tone is not evidence. Before you accept an output, check it against the task and a trusted source – for example the official document your solution draws on – and record what you found.

Why it matters

Real AI systems in the UAE, from smart-city services to healthcare triage, are judged not on whether they run but on whether they are fast, usable and correct; the build-evaluate-improve loop you practise today is exactly how professional teams optimise them.

Cross-curricular link · Mathematics · Design & Technology

Scoring outputs against fixed criteria is measurement in Mathematics. Building from a plan and iterating one change is the make-and-test cycle from Design & Technology.

Verify every output against a trusted source.

Core · Part 3 of 3 · Worksheet + Unplugged

Evaluate, then improve one thing

Change one variable at a time – that is how you know which change helped.

Read your output against each success criterion: is it efficient, is it usable, is it correct? Score it honestly – a fluent, confident answer can still be wrong, so verify it against the task and a trusted source. Where it falls short, change exactly one thing: the structure, an instruction, or the input. Run it again and compare before and after. Changing one variable at a time is how you know which change actually helped.

Unplugged activity – evaluate a build, on paper

You have built your signature solution. Working on paper, score its output against three criteria using a fresh input, then improve one thing. (Illustrative scenario: the canteen-menu helper, fresh input ‘Is Friday's pizza vegetarian?’)

Worked example. Score before/after: ‘Efficiency 3/5 → 4/5 after shortening the prompt.’
Week 8 Lab

Finish It, Then Prove It

This Lab is where your prototype becomes a finished, dependable solution: you complete every stage, run it again and again, keep an evaluation log, and make it behave well even when the input is awkward.

Previously

In the Core period you built and ran your solution once, scored it against your three criteria and changed one thing.

Scenario

You complete every stage of your solution and connect them, run it several times keeping an evaluation log, then feed a deliberately awkward input and add a graceful fallback so it fails safely rather than giving a confident wrong answer. (Illustrative scenario.)

Words to know

Tap a card to flip it and reveal the meaning.

Lab · Part 1 of 3

Finish it, then log it

A single run can be lucky.

In the Core period you built and ran your solution once. In the Lab you complete every remaining stage and connect them so the whole solution runs from input to output. Then you run it more than once, because a single run can be lucky. Keep an evaluation log: for each run, write the input you used – never personal data – and how the output scored on efficiency, usability and performance. The log shows whether your solution is really improving or just changing.

Why it matters

Public AI services in the UAE must stay reliable for every user, including those who enter something unexpected; logging evaluations and handling edge cases gracefully is exactly how real teams make a solution dependable, not just impressive.

Cross-curricular link · Mathematics · Design & Technology

An evaluation log of repeated runs is a data table read for trends in Mathematics. Designing for the edge case is robust design from Design & Technology.

Tool for this week: school-approved generative assistant (teacher-mediated) · optional Colab extension

1. Complete every stage of your solution and connect them so it runs start to finish. 2. Run it at least three times on different non-personal inputs and score each run in your evaluation log. 3. Feed a deliberately awkward input, add a graceful fallback, and document each fix. Stay safe: teacher-operated tool; non-personal inputs only. A graceful fallback must never expose data or give a confident wrong answer.

Lab · Part 2 of 3 · Worksheet

Keep an evaluation log

Repeated, scored runs turn improvement into evidence. Read the log, then document each fix.

Lab · Part 3 of 3 · Unplugged

Handle the awkward input

Fail gracefully – never with a confident wrong answer.

Real inputs are not always tidy – some are blank, strange or extreme (an edge case). A well-built solution does not give a confident wrong answer to these; it fails gracefully, returning a safe, readable fallback such as ‘input missing – please re-enter’ – or it flags the input, asks for clarification, or routes it to a person. Find one edge case, add a fallback, and document the fix: what broke, the single change you made, and how you verified the result. Always check accepted outputs against a trusted source before you trust them.

Unplugged activity – handle the awkward input, on paper

Your solution runs end-to-end. Working on paper, feed a deliberately awkward input and design a graceful fallback. (Illustrative scenario: the canteen-menu helper.)

Worked example. Graceful fallback: ‘If the input is empty, ask the user to rephrase rather than guessing.’
